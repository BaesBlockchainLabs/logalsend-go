# Logalty SDK for Go

A Go port of the Logalty `lgtweb` Java SDK 3.9.0, covering both halves of the
integration:

| Go package | Ports | What it does |
|---|---|---|
| `saml` | `com.logalty.generation.saml` | Builds and signs the SAML 2.0 assertions that sign a user in to LGT Portal |
| `wsdatachannel` | `net.logalty.sender.lgtportal.wsDataChannel` | The WsDataChannel SOAP service: send for signature, poll state, download documents |
| `xmldsig` | (Apache Santuario) | The XML Signature and Canonical XML 1.0 machinery the SAML half needs |

```go
import (
    "github.com/BaesBlockchainLabs/logalsend-go/saml"
    "github.com/BaesBlockchainLabs/logalsend-go/wsdatachannel"
)
```

Requires Go 1.21 or newer. Two dependencies: `github.com/beevik/etree` for the
XML tree model and `software.sslmate.com/src/go-pkcs12` for reading `.pfx`
keystores.

## Why you can trust the port

Cryptographic and wire-format code is not worth porting on the strength of
reading the original. Everything here is checked against the Java SDK itself,
running under JDK 21 with the vendor's own jars:

- **The signature.** A SAML assertion generated by the Go code is verified with
  **Apache Santuario** — the same library the Logalty portal runs — and passes
  both signature and reference-digest validation.
- **The canonicalizer.** Its unit tests reproduce, byte for byte, the
  `DigestValue` and `SignatureValue` that Santuario computed for a Java-generated
  assertion. Canonicalization is where an XMLDSig port silently goes wrong, so
  it is pinned against the real thing rather than against the spec alone.
- **The SOAP envelopes.** Twelve requests were captured off the wire from the
  Apache Axis 1.4 stubs, driven against a local recorder. The Go client
  reproduces all twelve.
- **The live service.** A shipment has been submitted end to end against
  Logalty's demo environment at
  `https://www.demo.logalty.es/lgt/lgtweb/wsDataChannel`: accepted with
  `retCode 0`, polled through to status 3, and a signer URL built for it with
  `buildSamlUrl`. Business-level rejections decode correctly too — a missing
  mobile came back as a structured `retCode 1` with the portal's own
  explanation.

`oracle/run.sh` rebuilds the Java harness and regenerates every golden file from
scratch. `oracle/` holds the three small Java programs it drives: `SamlRef`
(generate a reference assertion), `SamlVerify` (validate one with Santuario) and
`SoapCapture` (record what Axis sends).

Running it needs Logalty's own SDK, which is **not committed here** — it ships
without a licence to redistribute. Get
`lgtweb-sdk-full-dependencies-3.9.0.zip` from Logalty's integration portal and
unzip it into `java-sdk/`. The Go tests do not need it: the golden files they
read are committed under `testdata`.

Apart from the timestamps, a Go-generated assertion is byte-for-byte identical
to the Java one, down to the 76-column base64 wrapping.

## Signing a user in

Two different things in this integration are called SAML, and conflating them
wastes an afternoon:

| | `BuildSamlURL` (SOAP) | the `saml` package |
|---|---|---|
| Who it signs in | **the receiver** of a shipment | **your own staff** |
| Where it leads | the signing flow for one shipment | the LogalSend management portal |
| Who signs the XML | Logalty | you, with your `.pfx` |
| Guide section | 21 | 22 |

This section is the second one. It exists so that people in your organisation
reach the portal without a second password, and so that creating a user in your
system can create them in Logalty.

The assertion doubles as an **upsert**: send `Login` alone to sign an existing
user in, or send the provisioning fields too — `FullName`, `Mail`, `Role`,
`Group`, `Companies` — and the portal creates the user if they are new and
updates them if they are not. That is what lets you drive portal accounts,
roles and company visibility from your own directory instead of by hand.

If your integration is entirely API-driven and nobody on your side ever opens
the portal, you do not need this half of the SDK at all.

Before it works, your signing certificate has to be registered in the portal
under `#/administration/samlcertificates`, and `Config.ClientURL` must be the
company domain configured there.

The assertion is delivered by an **HTTP POST**, in a form field called
`saml_assertion`, to `<frontend>/saml/samllogin.pg` — a real server path, not
one of the single-page app's hash routes.

```go
keystore, err := saml.LoadKeystoreFile("/etc/logalty/client.pfx", "keystore-password")
if err != nil {
    return err
}

assertion, err := saml.NewGenerator(keystore).Login("www.example.com", "jsmith")
if err != nil {
    return err
}

// Serve this to the user's browser: it posts them into the portal and the
// session that comes back is theirs.
page := saml.SignInFormHTML("https://www.demo.logalty.es/lgt/frontendweb", assertion)
w.Header().Set("Content-Type", "text/html; charset=utf-8")
w.Write([]byte(page))
```

`saml.SignInForm` gives you the target URL and an encoded body instead, for
signing in from your own code rather than a browser.

Pass the output of `GenerateEncoded` or `Login` — the **encoded** assertion. The
portal expects Logalty's own percent-encoding in the field, and the form
encoding then goes on top of it. The double encoding looks wrong and is not:
the portal's own SAML tester percent-encodes the assertion in JavaScript before
submitting the form, so the server unwraps two layers.

The endpoint, the method and the field name all come from that tester page,
which the integration guide links from its section 22. Earlier versions of this
README guessed at a `?SAMLResponse=` query parameter; that guess was wrong on
all three counts.

Two limits worth knowing: the assertion the SDK builds is valid for **30
minutes** (`NotOnOrAfter`), but the portal **restricts access 10 minutes** after
the URL is generated, so treat 10 minutes as the real budget. And the signing
certificate has to be registered in the portal beforehand, under
`#/administration/samlcertificates`.

To provision the user at the same time, use `Generate`/`GenerateEncoded` with a
fuller `saml.Config` — see `ExampleGenerator_Generate`. Setting `Validate: true`
makes the generator insist that every provisioning field is present instead of
quietly emitting a partial assertion.

`LoadKeystore` takes the PKCS#12 bytes directly, for keys that come from a
secret manager rather than from disk.

## Sending a document for signature

```go
client, err := wsdatachannel.NewClient(endpoint, username, password, nil)
if err != nil {
    return err
}

result, err := client.ShippingSend(ctx, wsdatachannel.SendRequest{
    CompanyID: "311",
    TypeID:    "SIGNATURE",
    Receivers: []wsdatachannel.Receiver{{
        ExternalID:           "order-4711",
        ReceiverName:         "Ana",
        ReceiverEmail:        "ana@example.com",
        ReceiverIdentityID:   "12345678Z",
        ReceiverIdentityType: "NIF",
        ReceiverMobile:       "+34600000000",
    }},
    FileType:    "application/pdf",
    FileName:    "contract.pdf",
    FileContent: wsdatachannel.EncodeContent(pdfBytes),
})
if err != nil {
    return err        // transport, HTTP or SOAP fault
}
if err := result.Err(); err != nil {
    return err        // the portal accepted the call but rejected the shipment
}
```

All 25 operations are present: the four send variants (asynchronous,
synchronous, multi-receiver, template-driven), the three status queries, the
two SAML-URL builders, eleven download operations plus the general
`DownloadDocument`, the list export, and `CancelShipping`.

Errors come back typed: `*wsdatachannel.Fault` for a SOAP fault and
`*wsdatachannel.HTTPError` for anything else the endpoint says. Note the
two-level error model above — a successful call can still carry a non-zero
`RetCode`, which is what `Err()` surfaces.

### Field values the schema does not tell you

Learned from the Java SDK's own examples and from the live demo service:

- **`FileType` is a MIME type**, `application/pdf` — not the bare extension.
- **`Language` is a full locale**, `es-ES`.
- **Which `Receiver` fields are mandatory depends on the `typeId`.** Type 31210
  on the demo company rejects a receiver with no mobile
  (`retCode 1`, "ReceiverMobile is Empty"), so validate against your own
  shipment type rather than against the struct.
- **A `GUID` is not available immediately.** `ShippingSend` returns the request
  id with an empty GUID at status 1 ("Saved"); the GUID appears once the
  shipment reaches status 3. Poll by `ExternalIDs` to bridge the gap, which is
  the main reason to always set `Receiver.ExternalID`.
- **A `typeId` is not necessarily a signature flow.** Demo type 31210 is an
  identity-document validation: the receiver reads their ID card's NFC chip and
  the portal issues a "Declaración Electrónica de Atributos". There is no signed
  document at the end of it, so `DocumentSigned`, `DocumentStamped` and
  `DocumentOriginal` all come back empty and only `DocumentLogaltyCertificate`
  has content. Find out what your type actually does before building around the
  download you expect — see the service table below.

### Which service produces which document

A `typeId` is an instance of a *servicio*, chosen when the shipment type is
defined in the portal. The service decides what the receiver is asked to do and
therefore which downloads exist at the end. There is no API operation to list
the types configured for your company; they are visible in the portal when
creating a shipment type.

**For signing a document you want `Contratación`.** It is the only service on the
list that produces a signed document, which is what `ShippingDocumentSigned`
exists to return. The integration guide corroborates this from the other
direction: its sections on the synchronous send are titled *"sólo
contratación"*, so `ShippingSynchronousSend` and
`ShippingSynchronousSendWTemplate` only work for this service. If a synchronous
send is rejected, the shipment type is the first thing to check.

| Servicio | Produces | Download it with |
|---|---|---|
| **Contratación**, **Contratación Express** | **the signed document** | `ShippingDocumentSigned`, `ShippingDocumentSent` |
| Notificación | proof of delivery and reading | `ShippingDeliveryNote`, `ShippingNoticeReport` |
| Comunicación | one-way delivery record | `ShippingCertificate` |
| Custodia | archived evidence | `ShippingDossier` |
| Acreditación, Acreditación Express, Acreditación de Actas | evidence of an act | `ShippingCertificate`, `ShippingXmlCertificate` |
| Email Certificado, SMS Certificado | proof the message was sent | `ShippingCertificate` |
| Validación de Documentos de Identidad | "Declaración Electrónica de Atributos" | `ShippingIdCardCertificate`, `ShippingIdCardXmlCertificate`, `ShippingIdCardImages` |
| Verificación de Identidad | the same, lighter flow | as above |
| Videoidentificación Desatendida | video-identification certificate | `ShippingVideoCertificate` |

Every service also produces the Logalty certificate (`ShippingCertificate`),
which is the narrative record of what happened and is often the only artefact a
non-signing flow leaves behind.

Two caveats on this table. The service list is the one offered by the demo
portal, so yours may differ. And most of the mapping is inferred from the
service names and from which download operations the SDK exposes — the
`Contratación` and identity-validation rows are the two confirmed against real
shipments. A signed contract yielded `signed`, `stamped`, `original`,
`certificate`, `certificate-xml` and `evidence-pack`, and nothing else; the
identity-only artefacts came back empty, and vice versa. The difference between
`Contratación` and `Contratación Express` is not documented here because it is
not known; ask Logalty.

Two things worth knowing about a finished contract. `DocumentSigned` and
`DocumentStamped` return the same bytes — another alias pair, like
`DocumentLogaltyCertificate` and `DocumentIdentificationOCRCertificate` in the
identity flow. And `DocumentOriginal` returns the file you uploaded, byte for
byte, which makes it a cheap way to prove what was actually signed.

The signed PDF carries a real PDF signature: `/Sig`, a `/ByteRange` and an
`/AcroForm` holding the signature field. That is also why the portal refuses an
AcroForm on the way in — it adds its own.
- **Status does not update instantly.** A receiver's action can take tens of
  minutes to appear. `LastUpdate` staying equal to `SendDate` means "nothing
  recorded *yet*", not "nothing happened" — do not infer failure from it.

## Reading an identity verification

For an identity-validation shipment, the PDF certificate has a machine-readable
twin: `DocumentIdentificationOCRXML`. Parse that, never the PDF.

```go
doc, err := client.DownloadDocument(ctx,
    wsdatachannel.DocumentIdentificationOCRXML, wsdatachannel.IdentifyByGUID, guid)
raw, err := wsdatachannel.DecodeBinary(doc.Binary)
cert, err := wsdatachannel.ParseIdentityCertificate(raw)

if !cert.Passed() {
    return fmt.Errorf("verification failed: %+v", cert.FailedChecks())
}
fmt.Println(cert.Attributes.FullName(), cert.Attributes.IDNumber)
```

`cert.Passed()` is the check to make, **not** the shipment's status code: a
shipment reaches its final status whether the subject verified successfully or
not. It requires the portal's own verdict to be positive *and* every blocking
check to have passed.

What the certificate carries:

| | |
|---|---|
| `Attributes` | the identity data off the chip — document type and number, name and both surnames, sex, date and place of birth, address, nationality, issuer, expedition and expiry dates, and the chip's signed hashes |
| `Verification` | each check decoded into its real type: booleans for legal age and expiry, an integer retry count, and the four biometric scores as fractions of one (the PDF prints them as percentages) |
| `Checks` | the same rows as the PDF's validation table, each with the threshold applied and whether failing it is blocking |
| `Consents` | the consent-form answers, which the PDF does not expose at all |
| `Artifacts` | the embedded signed XML declaration and the PDF certificate itself, with `Decode` and `VerifyHash` |
| `Raw` | every code/value pair, so a code this SDK does not model still reaches you |

Two quirks worth knowing, both confirmed against a live certificate and handled
for you:

- **Attribute quoting is inconsistent.** The state attributes are plain, while
  the consent and artefact attributes wrap their values in literal single
  quotes.
- **The two embedded artefacts hash differently.** The signed result's digest is
  SHA-256 over its decoded bytes; the attributes declaration's is SHA-256 over
  its base64 *text*. `VerifyHash` accepts either and reports a genuine mismatch.

`lgtsend -attrs <guid>` prints all of this. Everything it prints is personal
data about the subject, so it goes to stdout and belongs nowhere near a log.

### Verifying a certificate offline

The XML certificates the portal issues are XMLDSig-signed, so `xmldsig.Verify`
can check one without contacting anybody:

```go
verified, err := xmldsig.Verify(certificateXML)
if err != nil {
    return err   // altered, or signed by nobody we can see
}
fmt.Println("signed by", verified.Certificate.Subject)
```

It checks both halves, because only one of them is not worth much: the
reference digest proves the content is what was signed, and the signature
proves that digest came from the certificate holder. It returns the signer's
certificate but does not judge it — check the issuer and the dates yourself.

Supported: inclusive Canonical XML 1.0, a single whole-document reference with
the enveloped-signature transform, RSA with SHA-1 or SHA-256. Anything else is
an error rather than a pass. In particular it does **not** handle XAdES
signatures with ID-based references, which is what the identity flow's
`idcard_nfcsigned_result` artefact uses.

> **One finding to take up with Logalty.** The contract flow's
> `certificate-xml` did not verify for us — and Apache Santuario, the reference
> implementation, rejects it too, with `signature INVALID` and
> `reference MISMATCH`. We tried all twelve canonicalization variants Santuario
> offers against the declared `DigestValue` and none matched, so the document as
> delivered is not the document that was signed. Our canonicalizer is not the
> problem: on that same file it produces output byte-for-byte identical to
> Santuario's, all 11,847 bytes of it. Something appears to change between
> signing and delivery. A certificate that cannot be verified offline is worth
> asking about, since that is much of what it is for.

Only `Status` 4 carries a meaningful `Result`; everything earlier reports 0.
Rather than compare codes by hand:

```go
state.Settled()   // it has stopped moving, one way or the other
state.Accepted()  // status 4 and result 7 — safe to download
state.Describe()  // "Finalizada / Aceptada", in the portal's own words
```

Two more limits from the guide: **`ShippingStatus` is deprecated** because it
only handles a single signer — use `ShippingStatusMultiReceiver`, which works
for one or many — and **`ShippingRequestList` accepts a range of at most 15
days**.

The web-service user also needs the *Solo Integración* role in the portal
(`saml.RoleWSIntegrationUser`), not an ordinary user role.

## Configuration

Copy `.env.example` to `.env` and fill it in. `.env` is gitignored; the example
is the committed template.

```sh
cp .env.example .env && chmod 600 .env
```

`lgtsend` reads `.env` from the repository root on its own, walking up from the
working directory, and never overrides a variable that is already set. For
anything else, source it:

```sh
set -a; . ./.env; set +a
```

## The `lgtsend` command

`cmd/lgtsend` is a small CLI that submits a shipment, polls it, and builds
signer URLs. It doubles as a worked example and as a way to reproduce a problem
for Logalty support.

Sending is irreversible and notifies a real person, so **nothing is sent unless
you pass `-send`**. By default it prints the exact SOAP envelope it would post —
captured through the real code path via a stub transport, not re-rendered — with
the password redacted and the base64 document elided.

```sh
export LOGALTY_USER=... LOGALTY_PASSWORD=...
endpoint=https://www.demo.logalty.es/lgt/lgtweb/wsDataChannel

# Inspect the request; nothing leaves the machine
go run ./cmd/lgtsend -endpoint $endpoint -company 7623 -type 31210 \
    -name Ana -lastname1 García -id 11111111H -idtype DNI \
    -email ana@example.com -mobile '+34555555555' \
    -external-id ORDER-4711 -file contract.pdf

# Send it
go run ./cmd/lgtsend ... -send

# Follow it, then get a signer URL
go run ./cmd/lgtsend -endpoint $endpoint -status ORDER-4711
go run ./cmd/lgtsend -endpoint $endpoint -saml <guid> -id 11111111H
```

With a populated `.env` the connection flags can all be dropped:

```sh
go run ./cmd/lgtsend -status ORDER-4711
```

`-debug` dumps the raw SOAP request and response, password redacted and
document elided. Reach for it when the decoded structs disagree with what the
portal shows on screen.

`-download <guid>` fetches every artefact the portal will part with, which is
the empirical way to find out how far a shipment got and what kind of flow it
was: a signed document exists only if something was signed.

```sh
go run ./cmd/lgtsend -download 001002-9996-000000000050255.par -out ./downloads
```

Downloaded certificates can contain the receiver's real personal data — name,
document number, date of birth, address and biometric scores are all in an
identity-validation certificate. Treat the output directory accordingly.

## Where this departs from the Java SDK

Deliberate changes, each for a reason:

- **Credentials live on the client.** Every Java operation takes `username` and
  `password` as its first two arguments; here they are `NewClient` parameters.
- **`context.Context` on every call**, so requests can be cancelled and
  deadlined.
- **Request structs for the wide operations.** `shippingSend` takes eight
  positional arguments in Java; `SendRequest` names them.
- **No temp directory.** The Java signer writes a scratch file it then deletes,
  a leftover from an older implementation. Nothing here touches the disk, so
  `SamlConfig.tempFolder` has no counterpart.
- **The password obfuscator is gone.** `Encrypt.EncryptStr` shifts the keystore
  password by a fixed key, and `SignXml` immediately shifts it back. The round
  trip is the identity function, so there is nothing to port — pass the real
  password.
- **One clock reading per assertion.** Java calls `new GregorianCalendar()`
  three times while building one assertion, so its `IssueInstant`,
  `AuthnInstant` and `NotOnOrAfter` can disagree by milliseconds. The Go version
  uses a single instant.
- **Deprecated methods are not carried over.** `buildLoginSaml`,
  `buildFullSaml` and the `tempFolder` overloads were already marked
  `@Deprecated` in the Java SDK.
- **Vendor spelling is kept.** `RemmitanceResult` is misspelled in the Java SDK
  and in Logalty's documentation; correcting it here would only make the two
  harder to cross-reference.

## Quirks reproduced on purpose

These look like bugs, and some are. They are kept because the portal has been
receiving them for years and the point of a port is to be accepted, not to be
tidy. Each is commented at its definition.

- **The mixed-prefix signature block.** Santuario builds the `<Signature>` with
  a `ds:` prefix throughout; the Java SDK then strips it from whichever elements
  exist at that moment. `Reference` and `KeyInfo` are created afterwards and
  keep theirs. The result mixes prefixed and unprefixed XMLDSig elements.
- **`AuthnContextClassRef` outside `AuthnContext`.** The Java XMLBeans cursor
  inserts the element beside its parent rather than inside it, leaving an empty
  `<saml:AuthnContext/>` next to it.
- **A hard-coded assertion ID** of `ass00000000002`.
- **A bespoke URL encoder.** Not `net/url`: the safe set is `-_.!~*'()`, hex is
  upper-case, space becomes `+`, and anything above U+00FF is dropped rather
  than percent-encoded as UTF-8.
- **Stray `xsi:type` attributes** on the `file` and singular `templateReceivers`
  SOAP parameters, which Axis emits because two descriptors in the stub
  disagree with their type registrations.
- **Alphabetical field order** in `Receiver` and `TemplateReceiver`, which is
  why `TemplateReceiver` reads `Field1, Field10..Field19, Field2, Field20,
  Field3...`. The schema declares a sequence, so the order goes on the wire.

Two things are *not* reproduced, because XML defines them as insignificant and
no parser can observe the difference: Axis escapes non-ASCII text as numeric
character references where Go writes UTF-8, and it orders the attributes of one
element differently. The wire-compatibility tests compare canonicalized XML for
exactly this reason.

## Security notes

The algorithms are inherited from the service, not chosen here: the portal
requires **RSA-SHA1** signatures with **SHA-1** digests, both of which are
obsolete. They cannot be changed unilaterally — the portal verifies with them.
If Logalty ever offers SHA-256, `xmldsig.EnvelopedSigner` is where it would
change.

`saml/testdata/test-logalty-private.pfx` is the throwaway test certificate that
ships inside the vendor's own SDK zip, with the password `111111`. It expired in
2022 and is only used to make the golden tests reproducible. Do not mistake it
for a credential.

## Layout

```

xmldsig/          Canonical XML 1.0 and enveloped RSA-SHA1 signing
```

publish this somewhere else.
